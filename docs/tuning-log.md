# 调参日志：16 秒漂移是怎么找到的

留档用。记录一次真实的排查过程，包括走过的弯路——因为下次遇到类似问题
（听起来「怪」但哪里都没报错），大概率还是同一个套路。

## 现象

30 分钟英文播客，出片后从中段开始能感觉到中文比画面慢，到片尾大概差一句半。
没有报错，`render_report.json` 里唯一可疑的数字是 `drift_max: 16.04`。

## 第一步：确认是累积延迟还是单点错位

在排布循环里记下每句的 `start_at - 原片 start`，按时间画出来。

- 如果是**累积型**：曲线单调上升，最后一段全是正数
- 如果是**单点型**：曲线在一处尖起，之后回到 0

结果是累积型，而且斜率跟「这一段的语速压缩比例」正相关。这就排除了
「某一句话错了」的可能，指向排布规则本身。

## 第二步：核算供求

逐句算两个数：

- **缺口** = 语音时长 / 语速上限 − 可用槽位（正数表示压到上限也塞不下）
- **富余** = 可用槽位 − 语音时长（正数表示还有空）

结果：59/182 句有缺口，总缺口 157 秒；总富余 464 秒。

**富余是缺口的三倍。** 这说明素材整体并不紧张，问题不在「装不下」，而在
「没有把富余的时间挪过去」。这一下就把方向从「加压缩上限」转到「改排布规则」。

## 第三步：找到那三个 bug

把排布循环逐行念一遍，找到三处：

1. 槽位用 `next_start - ideal_start`，而不是 `next_start - actual_start`
2. 单元切分用「320 个英文字符」当上限，与时间预算无关——320 字符译成中文
   要念 60 秒，而槽位只有 14 秒
3. 译文超长只能事后压语速，压到上限就无解

第 1 条是累积延迟的直接原因，第 2 条是缺口的来源，第 3 条是缺口的兜不住。

## 走过的弯路（重要）

**试过「借还」模型**：维护一个 `debt` 累加器，欠的时间在后续句子的空隙里
逐句还掉，上限 1.2 秒/句。

听起来很合理，实测**更糟**：因为 `target = ideal + debt` 让后面的句子开口
更晚，而真正的空隙本来就能被 `max(next_start, cursor)` 自然吸收。跑出来
最大漂移反而从 16.9 秒升到 27.9 秒。

教训：**延迟不是一个可以单独记账的量，它是 `cursor` 的函数**。任何额外的
账本都会和 `cursor` 打架。改成直接从 `cursor` 推，问题自己就没了。

这段代码已经被删掉，但留在 `docs` 里，因为「看起来更聪明的做法反而更差」
是这类问题最常见的陷阱。

## 最终数据

| 指标 | 旧实现 | 最终实现 |
|---|---|---|
| 最大漂移 | 16.9 秒 | 16.6 秒 |
| 平均偏移 | 0.99 秒 | 0.69 秒 |
| 偏移 > 1 秒的句数 | 36 | 28 |
| 压到上限仍塞不下 | 35 | 42（如实报告） |

最大漂移几乎没动，因为它是**一句译文长度是原声 4 倍**的异常句造成的，
排布救不了。真正的解法在翻译阶段：加上长度预算校验 + 超长重译之后，
同一份样本的最大漂移变成 **0.00 秒**。

## 如果只记一条

**漂移要在翻译阶段解决，不在排布阶段。**
排布只能让错误分布得更均匀，不能消除错误。
